# Self-paced seven-day Android challenge

Choose one small user problem. Finish one usable flow before adding features. This is a practice guide, not a scheduled community event.

| Day | Work | Evidence to keep |
| --- | --- | --- |
| 1 | Define the user, problem, and smallest useful flow. | One-page scope and acceptance criteria. |
| 2 | Build the core screen with sample data. | Screenshot plus empty/loading/error sketches. |
| 3 | Add the data source behind a repository interface. | Explain local vs remote data and failure handling. |
| 4 | Connect navigation and state. | Demonstrate the complete user flow. |
| 5 | Handle errors, input validation, and lifecycle behavior. | Reproduction steps for one failure and recovery. |
| 6 | Test the main behavior and polish accessibility. | Test results, device/API details, and remaining issues. |
| 7 | Record a demo and write setup instructions. | Repository, tested commit, demo, and engineering reflection. |

If adding AI, keep it to one feature and provide a deterministic fixture or fallback so others can explore the app without paid API access. Document configuration and costs; keep secrets out of the client and repository.

Before submitting, verify your README includes author credits, prerequisites, commands, screenshots, known limitations, license information, and one decision you would make differently. Ask another learner to follow the setup and record where they get stuck.
